XRootD

Extensions in XrdHTTP

XrdHTTP is the HTTP plugin of XRootD. This work adds a proper header parser, HTTP/2, Kerberos for HTTP, and a POSIX client that can run in the Linux kernel.

The long-term target is not “better curl”. It is kernel, RDMA, and GPU access to the same files, over a small set of storage operations.

Now

Kernel

Mount storage in Linux. Reads and writes go through the page cache. TLS stays in the kernel after handshake.

Next

RDMA

Same filesystem operations, but over RDMA instead of HTTP, for high throughput.

Next

GPU

Copy into GPU memory (DMA-BUF). HTTP cannot do that. It needs the RDMA path.

Introduction · goals

Three access paths, one operation list

The filesystem client defines operations (lookup, read, write, …) once. HTTP is the first transport. RDMA is meant to be the second.

See src/XrdXioFS/include/xiofs_ops.h: memory targets are page cache, user buffer, DMA-BUF, GPU. GPU ioctls exist and return -EOPNOTSUPP until RDMA exists.

Introduction · why XrdHTTP

The kernel needs HTTP verbs that XrdHTTP did not have

A kernel filesystem cannot speak the native xroot protocol. It can speak HTTP/1.1. So the server had to grow the missing methods, and a wire layer that HTTP/2 and HTTP/1.1 both use.

What we needed
  • Range GET for reads (page-cache fill)
  • PATCH with byte range for pwrite (not a full PUT)
  • PROPFIND for stat and directory listing
  • PROPPATCH / LINK for chmod and hard links
  • Many requests on one TLS connection (FUSE)
  • Kerberos for HTTP clients at KDC sites
What that is not
  • Not a new storage backend - still ofs
  • Not a replacement for root://
  • Not HTTP/2 inside the kernel (too much protocol)
  • Not GPU I/O on the HTTP path - kTLS copies into CPU pages
Why llhttp

Our parser was a line scanner, not an HTTP parser

On master, headers are read with BuffgetLine (scan for \n) and then parseLine (split on the first :). The code itself calls this “naive parsing”. That is enough for a friendly curl client. It is a poor base for HTTP/2, keepalive, and hostile input.

Problems with the own parser

  • It only understands complete lines. A header split across two reads waits until \n arrives.
  • It rewrites the receive buffer in place (inserts '\0').
  • Header values still carry \r\n; Connection is compared to "Keep-Alive\r\n".
  • No real grammar: a bad method or a huge incomplete header is easy to mishandle.
  • HTTP/2 headers are HPACK, not lines - this parser cannot be reused.

What llhttp gives us

  • A generated state machine (Node.js, MIT, vendored v9.4.1). It is the parser the web actually uses.
  • Incremental: feed whatever bytes are in the socket; it says when headers are complete.
  • Rejects malformed request lines and bounds incomplete headers (16 KiB, same cap as legacy).
  • Name/value callbacks fill the same XrdHttpReq as HTTP/2.
  • We still keep http.parser legacy so we can A/B and run the old tests.

This is not a speed project. On a typical GET the native line scanner is actually a bit faster (see the microbench). We switched so HTTP/1 is correct, bounded, and shares one request object with HTTP/2. Bodies, GET/PUT, TPC, checksums stay on master’s XrdHttpReq path.

Why HTTP/2

Many file operations on one connection

LAN / FUSE

A mount does parallel reads and writes. HTTP/2 keeps them on one TLS session. That is the main reason.

WAN

Fewer TCP/TLS handshakes for many small files. Useful, not the driver.

Kernel

The kernel module uses HTTP/1.1. HTTP/2 is too large (HPACK, streams). The kernel reuses the same methods (GET, PATCH, …).

Limits · Bridge

What has to change for parallel Runs

Native root:// already carries a stream id in the 24-byte header. The HTTP Bridge copies that field, then refuses a second Run() on the same link. Login stays once per connection.

Today, per HTTP connectionNeeded
One CurrentReq / XrdHttpReq One request object per HTTP/2 stream (map from nghttp2 id)
Transit::Run() fails if runStatus != 0 N in-flight Runs, keyed by xroot stream id, each with its own header buffer
One Result callback (XrdHttpReq) Done / Data / Error / Redir demuxed to that stream's writer
dispatchNext() waits for appInFlight Start the next stream up to a cap (e.g. 8 or 16 in-flight)
Process() 0 / 1 / close is the whole link A wait on stream 3 must not stop streams 1 and 5
File table and SecEntity are per link Keep that. Concurrent opens of different files; one identity

Not a thread per stream. The XRootD link is still one protocol object. Parallelism is several outstanding Bridge operations, the way a native client uses several stream ids. Redirect fan-out already gives cross-node parallelism without this work.

Architecture

HTTP/1.1 and HTTP/2 share one request handler

HTTP/1 request handling is the same as on master: after headers are parsed, the request still goes through XrdHttpReq and the Bridge. GET, PUT, HEAD, DELETE, WebDAV, TPC, checksums, and request bodies are that same code. Only header parsing is new (llhttp). HTTP/2 uses the same handler after nghttp2 assembles the headers.

Versus master

HTTP/1 is the same request path as master

An HTTP/1.1 client (curl, davix, XrdClHttp) still talks to the same XrdHttpReq and Bridge as on master. We did not rewrite GET/PUT/HEAD/DELETE or how bodies are read. What changed for HTTP/1 is only how request headers are parsed (llhttp). Set http.parser legacy to use master’s line parser.

HTTP/2

What was added

How the client selects HTTP/2

  • HTTPS: TLS ALPN token h2
  • Plain TCP: HTTP/2 connection preface, or HTTP/1.1 Upgrade: h2c
  • http.h2 off advertises only HTTP/1.1

Behaviour

  • PUT sends body as DATA arrives
  • Up to 100 streams queued; Bridge still one at a time
  • Flow control both ways; reset stream on RST_STREAM
  • http.h2push /path after a GET, if the client allows push

Needs libnghttp2 (BUILD_HTTP2). Tests: XRootD::httph2.

Kerberos

HTTP clients can use the site KDC

New on this branch. Native xroot Kerberos is unchanged. HTTP uses SPNEGO (WWW-Authenticate: Negotiate) and then logs into the Bridge as krb5.

Server

http.auth krb5 /etc/krb5.keytab HTTP/<host>@REALM

  • Service class is HTTP, not host
  • HTTPS required
  • Usually http.tlsclientauth off

Client

kinit then:

curl --negotiate -u : --cacert ca.pem https://host/file

  • 401, then the token on the same connection
  • Independent of HTTP/1.1 vs HTTP/2
XIOFS

POSIX client: CLI, FUSE, kernel

Userspace

xiofscli / xiofsd

HTTP/2. FUSE multiplexes I/O on one connection. Used to develop and test the methods.

Kernel

xiofs.ko

Linux page cache. HTTP/1.1 on a kTLS socket. Handshake is still userspace (xiofsagent).

The native parser still wins

Apple Silicon, RelWithDebInfo xrootd, parse compiled -O2. Median of three runs. Parse: 200k iterations of a typical GET. Request loop: one keepalive connection, sequential, local xrootd, cleartext (HTTP/2 = h2c). Same XrdHttpReq after headers.

Native = master’s BuffgetLine / split-on-colon scanner. It still wins the parse microbench; we did not switch for speed. HTTP/2 on one stream is about 1.4× after nghttp2 NO_COPY + batched writev (no memcpy of the body into frames). Remaining gap: HPACK, 16 KiB DATA frames, serial Bridge. True sendfile like cleartext HTTP/1.1 is not possible - each DATA frame needs a 9-byte header.

Outlook

Status

Done
  • llhttp + HTTP/2 on the server
  • Kerberos for HTTPS
  • PATCH, PROPPATCH, LINK
  • FUSE client (HTTP/2)
  • Kernel module + kTLS (CPU / page cache)
Not done
  • RDMA transport
  • GPU-direct (ioctl stub only)
  • HTTP/2 in the kernel
  • Automatic TLS reconnect
  • Parallel Bridge (true parallel I/O on one HTTP/2 connection)
  • Symlinks, chown, utimens
Next steps
  • Land parser + HTTP/2 + Kerberos on master
  • Keep XIOFS as the follow-up
  • RDMA when XrdHTTP (or a sibling endpoint) can serve it
  • Then GPU I/O on DMA-BUF

Today: CPU applications can mount XrdHTTP and use the Linux page cache. RDMA and GPU are designed in the client API, not implemented on the wire.
